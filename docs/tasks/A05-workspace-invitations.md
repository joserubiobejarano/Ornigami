## Scope and existing contract

A05 implements the team lifecycle portion of E09: invitation expiry and reinvitation, three-seat Complete plan enforcement, owner revocation of pending invitations, owner removal of accepted members, and preservation of an invitation return path through account signup/login. E09 integration still depends on shared writer coordination and owner decisions below. Complete's three seats include the owner and unexpired pending invitations. An invitation is valid for seven days, belongs to one business/email, and can be accepted only by a signed-in, email-verified account matching the invitation.

The baseline had two lifecycle defects. A partial unique index used only `accepted_at IS NULL`, so an expired invitation continued to reserve its business/email pair forever. The API also counted seats in independent queries before inserting an invitation or membership, allowing concurrent requests to exceed capacity. It had no owner revoke/remove operations. Invitation signup already uses the A04-safe `callbackUrl` path: `/signup?invite=...` resolves to `/team/invite/...`; A04 stores that callback with the verification token and returns it to login; Auth.js accepts only same-origin return paths. Preserve this contract and verify the full browser path in focused tests.

## Implementation result

`team_invitations` now tracks `pending`, `accepted`, or `revoked`, with `accepted_at` and `revoked_at`; the partial unique index reserves one pending email per business, while accepted/revoked rows release that key. Legacy accepted rows are backfilled. Reinviting after expiry rotates the token hash, expiry, inviter, and creation time on the same pending row. Only the SHA-256 token digest is stored. Invitation email keeps its existing seven-day lifetime and no provider behavior or dependency was added.

`POST /api/team` reserves a seat only for the canonical business owner with active Complete access. The reservation includes the owner, accepted members, and unexpired pending invitations; it returns conflict for a full seat or a still-live duplicate. A sent email returns no raw link. If delivery is not configured, the owner receives the invite URL for manual sharing. A provider exception removes only the matching invitation id/token-hash reservation, so a concurrent reissue cannot be deleted accidentally.

`POST /api/team/invitations/[token]` accepts by bearer token only after live DB checks for a verified same-email user, active Complete access, and workspace admission. Its PostgreSQL function adds the member and consumes the invite in one call. It counts accepted seats plus all other unexpired pending reservations, including legacy over-reserved rows, before accepting. The UI requests JSON and navigates only after explicit success; the same POST endpoint returns a constant 303 redirect for non-AJAX clients.

`DELETE /api/team/invitations/[token]` treats a UUID path value as the invitation id and marks a pending invite revoked. `DELETE /api/team/members/[userId]` deletes only a non-owner membership and revokes any pending invitation for that member's email. Re-revoking returns 409; removing an absent member returns 404; removing the owner returns 409. The owner can revoke/remove during lapse or downgrade as a limited recovery action. Mutations require an authenticated session and reject cross-origin or unmarked requests; routes log unexpected failures and return generic server errors.

`GET /api/team` derives member versus owner from canonical A02 business ownership, not the legacy membership role. It lists live invitations and retains membership visibility for authorized workspace members. The UI displays expiry in UTC, updates the local seat count as a reservation expires, asks for confirmation before revocation/removal, disables invitation creation at the seat limit, and permits owner cleanup controls when Complete access is unavailable. Signup and login links retain the same invitation return path via A04 `callbackUrl` storage through verification and Auth.js.

## Shared integration changes

- **Database dependency:** migration `021_workspace_invitations.sql` is reserved for A05 after A04 migration 020. It adds invitation status/revocation fields, a lifecycle consistency constraint, a partial unique index over pending invitations, and SQL lifecycle functions. Its status backfill changes legacy accepted rows from pending and leaves revoked rows revoked on reapplication. Expired invitations are reissued by rotating the stored token hash and expiry on the same pending row. Keep migration 018/019 reservations intact and maintain `neon/README.md` plus `docs/DATABASE.md` during integration.
- **Model and routes:** apply migration 021 before using the changed `GET|POST /api/team`, `POST|DELETE /api/team/invitations/[token]` (POST uses the bearer token; DELETE uses the invitation UUID), and `DELETE /api/team/members/[userId]` routes. Shared database types are inferred from query results; integration should update any central invitation types if introduced later.
- **Serialization:** Neon serverless uses HTTP transactions via `sql.transaction([...])`; it does not support interactive transactions. The implementation performs each mutation in one PostgreSQL call to `team_reserve_invitation`, `team_accept_invitation`, `team_revoke_invitation`, or `team_remove_member`; seat-sensitive functions lock the business row before checks and writes. Reservation includes accepted seats and all unexpired pending invitations. Acceptance includes its own pending reservation when checking the post-accept count, so legacy over-reserved invitations cannot all consume seats beyond three. The PL/pgSQL checks run as separate statements in one invocation, which uses the default READ COMMITTED isolation and sees commits after row-lock waits. External writers touching the same admission state must lock in `business → user` order; route refactors must retain atomic checks/writes. Existing business provisioning and billing-agent writers do not yet participate in this mutex; see the required integration proposals below.
- **Authorization and CSRF:** derive role from canonical A02 `BusinessContext`/`businesses.owner_user_id`, never a historical `business_members.role` value. Owner mutations require an authenticated canonical user, explicit owner authorization, and fail-closed same-origin/CSRF validation. A removed member must fail canonical resolution for the original business; Review Booster mutation helpers also check the live `business_members` row. Do not remove or rewrite shared Google/provider data as part of membership removal; A08 owns its shared owner-keyed connection lifecycle.
- **Shared integration:** A02/A00 should align concurrent business provisioning (`getOrCreateBusinessForUser`) with the business/member locks before claiming global single-workspace admission is race-free. A03 billing writers that alter `business_agents` should lock the business row before entitlement changes, so admission checks serialize with downgrades/expiry. A11 privacy export should include invitation records/status and revocation timestamps where account/workspace ownership permits; deletion/retention behavior for invited-user email data needs a retention decision. These are integration contracts, not changes made by A05.
- **Dependencies:** no npm package, package/lockfile change, or environment variable was added. Integration must apply migration 021 before activating code that reads/writes its new columns/functions. A04 migration 020 remains a prerequisite for the auth callback path used at rollout.

## Access, downgrade, and product decisions

Membership removal immediately revokes access to the original workspace through A02 context and live member checks. Workspace-owned records remain in place. Routes that require a business but use A02's contextless first-business provisioning may create a separate personal workspace for a removed user; that does not restore access to the removed workspace. A08 should review owner-keyed Google data separately before any cleanup.

A18's Complete downgrade timing, excess-seat policy, and member read access after lapse are recommendations awaiting owner approval. A05 must preserve current billing/entitlement behavior and avoid silently removing members or imposing scheduled downgrade rules. Integration with A03 must decide how a future downgrade is reconciled with existing memberships and pending invitations before enabling such a policy. No downgrade behavior is approved by this handoff.

Expired or revoked bearer links both show an unavailable invitation page. Acceptance failures return a generic invalid/expired message when no live token exists. Existing response semantics are 409 for a repeated revoke, 404 for a repeated/absent member removal, and 409 for owner removal; the owner is never a removable membership row.
