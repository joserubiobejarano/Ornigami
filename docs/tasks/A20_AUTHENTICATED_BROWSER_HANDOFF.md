## Reproductions and integration request

On the final candidate, the UI reproductions are:

- Booster Settings → Save settings (`POST /api/review-booster/settings`)
- Add a visit → Save visit, with either an empty or valid synthetic form (`POST /api/review-booster/visits`)
- Replies inbox → Save draft (`POST /api/reviews/draft`)
- Replies Settings → Remove → Confirm removal (`DELETE /api/team/members/:id`)

Each showed the cross-origin guard message and left the fixture snapshot unchanged. Fourteen sanitized mutation request rows were recorded on the final runtime. They show browser Origin, Host and `Sec-Fetch-Site: same-origin`; configured Auth URL origins and logged Next internal `initURL` origin are `http://127.0.0.1:61948`; forwarded host/proto are absent. The earlier f4ea receipt names this diagnostic field `requestUrlOrigin`; the final c9a28b3 evidence names it `nextInitUrlOrigin`. Both refer to Next internal `initURL` metadata, not evidence of the final handler `Request.url` consumed by `isSameOriginMutation`. Browser tooling does not expose response events, so UI/API correlation is the unique route-ledger record plus the visible guard response. This evidence does not identify which actual handler-side value causes rejection.

The integration session should inspect or safely instrument the actual handler `Request.url` and relevant headers, identify the failed same-origin predicate, and apply a narrow canonical-origin correction only if supported by that evidence. Preserve cross-site rejection coverage. Then rerun owner settings/intake/draft writes, outsider/member authorization mutations, member removal plus the same persisted member session, and draft persistence/conflict. Do not weaken the guard or spoof Origin. No shared app source, model, route, setting, or dependency was changed here; the canonical-origin proposal remains subject to that investigation.
