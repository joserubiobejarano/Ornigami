Dependencies were installed privately for this worktree; package manifests and lockfile were not changed. Do not merge or deploy from this worktree.

## Shipped behavior in this worktree

- Checkout, plan change, and billing portal use A02 `requireBusinessOwner`, which resolves an already persisted canonical actor/business owner context without bootstrapping a workspace. Members and callers with no/invalid persisted business receive 403 before Stripe access. Existing browser checkout and portal requests retain their login redirect. The dashboard billing page resolves its workspace before rendering these forms.
- Checkout uses the canonical owner’s persisted email and an owner-scoped Stripe customer mapping. It never searches Stripe by email, never replaces a failed customer retrieval with a newly created customer, and stops on conflicting owner/business mappings. Ambiguous customer creation is reconciled by Stripe customer metadata `owner_user_id`; a missing result past the provider idempotency window remains blocked for manual reconciliation.
- Checkout saves one immutable Stripe request payload and stable provider idempotency key per unresolved business intent. The saved request includes the customer, selected price, trial choice, return URLs, metadata token, and a 23-hour Stripe expiry. Retries recover by saved session ID or exhaustive Stripe session listing by the immutable metadata token; only a confirmed expired session can be retired. An unresolved request older than Stripe’s idempotency retention window stays blocked.
- Concurrent/retried checkouts use the persistence claim and fence, and conflicting plan requests return a recoverable 409. A provider response followed by a database write failure is recovered from Stripe metadata without creating another session.
- Trial checkout follows the approved policy: one 14-day trial per business and billing owner, consumed only by authoritative Stripe trial start. Abandoned checkout does not consume the trial. Used or unknown legacy history creates paid checkout without another trial; unknown legacy status still needs operator reconciliation before a trial can be granted.
- Before a new checkout, local subscription IDs for the selected business are retrieved from Stripe, then all provider subscriptions on the owner customer are paged. Any nonterminal subscription for the selected business blocks checkout; a live subscription for another business owned by the same customer can coexist when its business/customer mapping is validated. Unmapped or cross-owner live subscriptions block for reconciliation.
- The portal uses only a reconciled owner customer mapping. It does not provision customers when the mapping is absent or Stripe retrieval fails. Plan changes validate the selected business, local subscription link, owner customer, and provider subscription before preserving the current immediate `always_invoice` behavior.

Only the one-time trial policy was approved for this work. Other A18 proposals, including quota windows, grace, and downgrade timing/seats, remain pending approval.

## Integration contract and boundaries

- A02 is a prerequisite. Routes consume `requireBusinessOwner`; email is not used as identity. Keep the persisted-business/no-bootstrap behavior when integrating.
- A00 shared follow-up: serialize canonical workspace bootstrap in `api-security.ts` / `db/businesses.ts` so simultaneous first-use requests cannot create multiple businesses. Migrate the billing page away from its email-to-user fallback and ensure its workspace setup path persists the business before the forms are used; that shared change is outside A03 scope.
- Persistence and webhook changes reserve migration **019**. It ensures `business_agents.plan_id`, `business_agents.billing_period`, and `subscriptions.current_period_start` exist, plus nine tables: `billing_migration_receipts`, `billing_checkout_intents`, `billing_owner_customers`, `billing_customer_provisioning`, `billing_trial_business_history`, `billing_trial_owner_history`, `billing_trial_reservations`, `billing_reconciliation_leases`, and `billing_webhook_events`. It also adds SQL claim/finalize/lease/snapshot functions. The checkout partial unique index permits one pending/uncertain intent per business; completed intents remain blocking in the claim function until cancellation is authoritatively reconciled. A00 should review and apply all of migration 019 in one database transaction before deploying these routes or webhook code. Checkout relies on the SQL claim/fencing functions; webhook reconciliation alone consumes trial history.
- Webhook reconciliation resolves only persisted customer/subscription mappings, acquires an owner/event fence, retrieves current Stripe subscription state, and derives plan plus billing period from the actual single subscription price. Its SQL snapshot transaction updates `subscriptions`, the legacy owner `profiles` plan mirror, both `business_agents` mirrors, retires the replaced subscription mirror when Stripe confirms a terminal state, consumes both trial history identities, retires matching checkout intents, and marks the event complete atomically. The profile plan is a compatibility mirror and cannot represent multiple businesses reliably; A02/A06 must use business-scoped authoritative billing fields for entitlements and quotas. Out-of-order live-subscription conflicts, unknown mappings/prices, busy/pending duplicate deliveries, and stale fences return HTTP 500 so Stripe retries. An already completed event returns a duplicate success.
- Stripe documents that webhook events may arrive out of order and recommends deduplication by event ID; this is why reconciliation retrieves the current Subscription and applies a fenced current-state snapshot. See [Stripe webhook delivery behavior](https://docs.stripe.com/webhooks#event-ordering).
- Checkout refuses to blindly reuse an unresolved idempotency key after the retention window because Stripe may prune keys once they are at least 24 hours old and treat reuse as a new request. The route instead reconciles by immutable session metadata, redirects to an open session, blocks completed sessions, and rotates only after confirmed expiration. See [Stripe idempotent requests](https://docs.stripe.com/api/idempotent_requests), [list Checkout Sessions](https://docs.stripe.com/api/checkout/sessions/list), and [expire a Checkout Session](https://docs.stripe.com/api/checkout/sessions/expire).
- A06 must read business-scoped `plan_id`, `billing_period`, current period bounds, and subscription ID from authoritative reconciled billing state. The only approved A03 policy here is trial eligibility; A06 owns its quota-window proposal and requires separate approval.
- A11 should use `cancelMappedOwnedBillingSubscriptions` for locally mapped owner subscriptions under the same owner fence, define privacy-compatible retention for both trial-history identities, and not treat an app-side checkout result as proof that billing was canceled. The helper requires consistent customer/subscription/business mappings and confirmed Stripe cancellation; it does not discover Stripe-side orphan subscriptions or unresolved checkout sessions. A11 must freeze deletion and reconcile those provider objects before removing mappings.
- A05 owns seat enforcement and downgrade compatibility. The existing immediate plan-change/proration behavior remains. Next-period downgrade policy and blocking seat-reducing changes are not approved by this implementation.
- A13 should make the pricing/billing CTA reflect eligibility. Existing shared UI says “Start free trial” even when consumed or legacy-unknown history means checkout proceeds without a trial; changing that shared UI is outside this A03 route scope.
- `isPlanId` in the shared billing catalog uses `value in PLANS`, which accepts inherited keys such as `constructor`. A03 routes use a strict local plan guard; A00 should harden the shared helper for other consumers.
- No dependency or shared deployment-setting changes were made in this route slice. Stripe secret, price, webhook, and URL settings keep their existing names and owners.
- No ROADMAP or other shared documentation was edited. No staging/production deployment was performed.
