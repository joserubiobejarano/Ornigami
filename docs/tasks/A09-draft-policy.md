# A09 draft policy handoff

The proposed [migration 024](./A09-draft-schema.sql) adds one policy/version row per review and an owner-profile reservation counter. It is not installed by this branch. Migration backfill keeps all existing `review_replies` rows and points policy state at the latest relevant row. Existing unposted drafts become `human_edited`, version 1; replies already reflected as posted stay `posted`. A draft save appends a new reply row and compare-and-swaps the expected version, so concurrent saves cannot erase each other.

Generation uses a two-minute per-review claim with a monotonic fencing number. It skips any saved or replied review before provider generation. Owner usage is reserved against the existing 2,000 reply safety limit and the current Stripe period. Empty output, provider failure, stale claims, and a human edit racing generation release the reservation. A successful generated draft and its usage charge commit in one PostgreSQL function. Generic sample generation uses the same reservation and commit/release functions.

Posting checks the saved version and exact text at the server boundary. A manual Post action is the approval and atomically moves the matching AI or human draft to `approved`; automatic posting additionally requires the owner's saved opt-in, a stored four- or five-star rating, and an entitled business. Posted state and the local review reply update commit together after Google accepts the request. Definitive provider rejections release the fence. A transport failure, server error, or local persistence error retains the fence because Google may already have accepted the reply; there is no automatic retry. The current package has no explicit operator reconciliation path for that uncertain result, so integration must decide how an owner or support operator confirms remote state and clears a fence safely.

The accounting field remains owner-profile-wide, as the existing `review_replies_used` model does. A business billing period later than the stored owner period starts a new window; an older business period does not roll the owner counter backward. When billing metadata and the saved period are both missing, the first reservation stores one stable timestamp after taking the owner profile lock, and parallel reservations share it while retaining the existing used count. The reservation total is recomputed from active ledger rows under that same lock, so expired reservations and cascaded business deletion do not permanently consume capacity; the denormalized reserved counter may lag after a cascade until the next reservation. Two businesses owned by one profile can still have different Stripe period boundaries; a single profile counter cannot represent both independent windows perfectly. Keep that owner-wide behavior until A00/A18 resolves the shared accounting model. The shared usage reader should include outstanding reservations if other callers continue using it.

Integration dependencies are proposed migration `024`, the owned review routes and settings/UI contracts, and A08's existing selected-location and provider helper. `src/lib/usage.ts`, shared billing/deployment configuration, dependencies, and roadmap are unchanged. No new package is required. Apply the migration before deploying any route that calls its `a09_*` functions, after normal integration review. A11 should include both new tables in account export/retention and test deletion/expiry cleanup.

Validation in this worktree: disposable PostgreSQL 17 applies migration 024 twice, verifies legacy preservation, racing same-version saves, concurrent quota reservations, atomic generation charge, human-edit fencing, expiration/period rollover, safe automatic posting, low and unknown rating denial, explicit manual posting, stable missing-period accounting, and production TypeScript wrapper round trips. Separate A08 provider tests use request mocks and do not establish live Google acceptance.
