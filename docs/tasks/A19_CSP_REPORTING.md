# A19 CSP reporting hardening

`POST /api/csp-report` accepts legacy `application/csp-report` reports, Reporting API `application/reports+json` CSP violation batches, and `application/json` for compatibility. Unsupported declared media types receive 415. The handler accepts only recognized CSP report fields, caps the body at 16 KiB, retains at most five reports, limits stream chunks, and uses one five-second read deadline. Oversized bodies receive 413; invalid encoding, stalled/churned streams, and malformed JSON receive 400.

Violation logs use a fixed event name and a normalized field allowlist. URLs contribute only their scheme (`http` or `https`); paths, query strings, fragments, userinfo, host labels, data URLs, and malformed input are not retained. The fixed Trusted Types blocked URI markers `inline`, `eval`, `trusted-types-sink`, and `trusted-types-policy` are preserved for sink-level diagnosis; arbitrary malformed values are not. Directives are reduced to known CSP directive names, disposition is reduced to `report`, `enforce`, or `unknown`, and numeric fields are range checked. This intentionally gives up host/path level diagnosis because both report contents and host labels can be forged or contain user tokens. CSP reports are unauthenticated browser input and remain spoofable even after normalization.

The route relies on the existing `checkPublicWriteRateLimit` database-backed limiter and `getTrustedRequestIp` ingress-aware address extraction. It returns 429 when limited and a static 503 when the limiter is unavailable. Integration must retain the shared limiter and configure ingress so client-supplied forwarding headers cannot become the trusted IP; this task does not alter those shared components or deployment settings. No report database table or third-party reporting provider is introduced.

Runtime browser collection and deployed ingress header behavior remain integration acceptance items.
