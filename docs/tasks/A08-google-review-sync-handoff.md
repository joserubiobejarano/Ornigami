# A08 Google review sync and replies handoff

This isolated patch implements review fetching, persistence, and provider reply posting against a business's explicitly selected Google Business Profile location. The manual sync and cron share the same bounded persistence helper. The cron processes only selected locations that still belong to the business owner and have a connected owner integration. Both the selected-location lookup and cron also require the cached location's `connection_version` to match the current OAuth connection generation, so an OAuth reconnect immediately invalidates older location cache entries until discovery refreshes them.

`POST /api/google/reviews/sync` accepts optional `businessId` in the query or JSON body and optional `locationName` in the body. Query/body business IDs must agree. The route requires active Review Replies access for the resolved business and fetches only its selected location; a requested location must match that selection. A successful response remains `{ "imported": number, "new_reviews": number }`. It requests at most 50 reviews per Google page, follows no more than the configured page limit, rejects repeated page tokens and duplicate or malformed review resources, and saves nothing if provider pagination fails. Upstream rate limits return 429, an upstream 503 returns 503, and other provider failures return 502. A numeric `Retry-After` header is forwarded only when it is at most one day.

`POST /api/google/replies` accepts `reviewId`, `locationName`, `reply`, and optional `businessId` in the body, with an optional `businessId` query parameter. It rejects conflicting business IDs. Before contacting Google, the server resolves active business access again, checks the selected location, and finds the stored review using the exact business ID, selected canonical location name, and review ID. It sends a `PUT` to the canonical v4 reply resource with `{ "comment": reply }`. Reply text is limited to 4096 UTF-8 bytes. Google response bodies are not returned to clients. If Google accepts the reply but the local status update fails, the endpoint returns a safe 502 message so the owner can sync and retry the idempotent provider operation.

Review rows use the integration owner's user ID and the selected business ID. Upserts use bounded `jsonb_to_recordset` batches of 250, leave a different-location conflict untouched, and preserve an existing local `replied` status and reply text when Google returns no reply. New review alerts are emitted only for newly inserted rows. Existing draft creation, reply generation, and draft persistence policy are unchanged.

The runtime depends on the shared A02 business context and entitlement helper, the Google selected-location lookup and selection table, `connection_version` fields on the Google connection/location rows, and canonical URL builders from `google-resources`. The paired schema proposal is [A08-selected-location-schema.sql](A08-selected-location-schema.sql). Integration must install that schema before enabling these routes; this patch does not add a migration or apply the proposal to a shared database. No package dependency was added.

Legacy review rows may still store `locations/{id}` without the account segment now required for canonical API calls. [A08-canonical-resource-backfill.sql](A08-canonical-resource-backfill.sql) is a separate dry-run-by-default proposal. It lists every eligible or ambiguous candidate, then rolls the transaction back. To apply it, integration must inspect the candidate output and deliberately replace the final `ROLLBACK` with `COMMIT`. It upgrades only rows with an explicit same-business selected location and one matching cache entry from the current connected credential generation. It leaves account-ambiguous and unselected-business rows unchanged. Rediscovery alone does not choose a selected location or rewrite review rows.
