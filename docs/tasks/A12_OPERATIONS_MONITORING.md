# A12 operations monitoring handoff

Status: implementation proposal for integration review. It was built in the isolated `Ornigami-A12-operations-monitoring` worktree. No shared roadmap, workflow, deployment setting, or shared/live database was changed. Migration 027 is reserved and the SQL in [A12_CRON_SCHEMA.sql](./A12_CRON_SCHEMA.sql) has not been applied; PostgreSQL validation used a disposable local test cluster only.

## Cron contract

`src/lib/cron-health.ts` owns fixed job identities (`review_booster`, `review_replies`, `privacy_retention`) and exports:

* `acquireCronJobRun(job, { leaseMs?, budgetMs?, batchLimit? })` atomically claims a durable lease and returns `{ runId, fence, cursor, deadlineAt, batchLimit, budgetMs }`. Defaults are a 45-second budget and 90-second lease; all values are clamped, and lease is at least budget plus 15 seconds. `CronLeaseBusyError` means return HTTP 409 with `Retry-After`; any health-store failure throws, so work must not start.
* `checkpointCronJobRun({ runId, fence, cursor, processedCount, unitCursor? })` durably saves job JSONB continuation state and renews the lease through a 15-second terminalization grace after the run deadline. Optional `{ businessId, cursor }` state upserts/clears a per-business unit cursor in the same fenced statement. It rejects an expired lease or obsolete fence.
* `finishCronJobRun({ runId, fence, status, processedCount, failedCount, errorCode?, outcomes?, clearCursor? })` supports `succeeded`, `partial`, `failed`, and `no_work`; the fenced terminal update locks the state row before the run row and rejects stale owners. It remains available during the terminalization grace after the work deadline. `partial` keeps the cursor; success, no-work, and explicit `clearCursor` clear job and child unit cursors atomically. Outcomes are sanitized counts and booleans keyed by fixed table-operation names.

Workers must check `deadlineAt` before admitting another external operation, checkpoint only after a durable unit, and leave the previous cursor unchanged if that unit times out. On budget exhaustion, finish `partial` with `errorCode: 'budget_exhausted'`; this continuation is expected and is not raised as a failure alert. Use `partial_failures` or `job_failed` for actionable failures. A stale fence must stop all further effects. Claiming state is the health write that precedes provider work. The 45-second application deadline controls new admissions; it cannot cancel an already-running database statement. Integration must verify a Neon/client statement timeout below the remaining run budget so a slow query cannot outlive lease terminalization.

The privacy helper must pass per-operation `{ deleted, failed, complete }` counts. Never pass provider errors, IDs, email, request bodies, comments, or exception strings. Its bounded batch and continuation behavior is documented in [A12_PRIVACY_CLEANUP.md](./A12_PRIVACY_CLEANUP.md). Legacy unfenced `startCronRun`/`finishCronRun` functions were removed after all three cron routes adopted the durable claim API.

## Monitoring and privacy

`src/lib/cron-alerts.ts` monitors failed/partial/stale state for all three jobs. It detects never-run and missed cadence only for Booster (hourly) and Replies (every four hours), with a two-cadence grace window; privacy retention remains unscheduled by default and has no inferred cadence. A migration-owned PL/pgSQL function serializes candidate refresh, resolution, and dedup claims with a database advisory lock. Alerts deduplicate durably per job/reason and repeat no more than every 30 minutes while active. A resolved alert can fire immediately on recurrence. Sentry events contain a whitelisted fixed message and fixed tags only. Missing DSN and transport failures increment durable error counters and emit sanitized operational logger events; failed transport retries after five minutes.

The authenticated health endpoint returns recent job summaries, durable cursor presence/checkpoint timestamps, and active alert metadata. It does not expose legacy `error_message` contents or cursor values. The health GET evaluates monitoring, and every finished run also evaluates it. Integration should retain an independent, authenticated monitor invocation so never-run/missed jobs are noticed even when no worker completes; existing hourly/four-hour workflow cadence can drive that invocation without adding a new deployment setting. A privacy cadence is an explicit operator decision.

The schema proposal scrubs existing raw cron error text when applied, adds constrained statuses and durable job/unit state and alert-dedup tables, plus an advisory-lock serialized claim function. Per-business unit cursors cascade with workspace deletion. It does not change any existing scheduler. Replies uses a per-business unit cursor for location/stage/review progress while the global cursor advances by business key; unfinished unit cursors are resumed after keyset wrap, so a large tenant does not block work for later tenants. Booster relies on its durable delivery ledger and candidate selection to recover visit progress within a business, then persists a separate full-pass flag when another bounded pass is needed; it does not store a separate visit-ID cursor. See [A12_CRON_BUDGETS.md](./A12_CRON_BUDGETS.md) and the shared [cron budget helpers](../../src/lib/cron-budget.ts) for provider admission windows. Before migration/consumer deployment, integration must drain old workers and apply migration 027. Shared migration registration and application order remain integration-owned. Keep the existing configured `NEXT_PUBLIC_SENTRY_DSN` wiring; this task adds no environment variable or deployment setting.

## Shared-file contracts and integration dependencies

The three scheduled `GET` consumers use the health helpers as one contract: authorization precedes lease acquisition; `409` plus `Retry-After` means the existing job owns the lease; health-store acquisition/checkpoint/finish failures return `503`; resumable `partial` work returns `202`; actionable run failures return `500`; completed and empty runs return `200`. `/api/cron/health` remains cron-authenticated, returns only summary/outcome/active-alert data, reports `healthy:false` when alerts are active, and returns `503` when alert evaluation or health reads fail. Manual review/Booster flows do not acquire cron leases; optional scheduler callbacks and provider signals preserve their existing defaults for those callers.

| Owner | Required integration |
| --- | --- |
| A06 Booster | The GET route claims the lease before processing and checkpoints settled runner progress. Candidate delivery claims and the durable delivery ledger recover visit outcomes; a global business keyset and full-pass flag resume bounded candidate sweeps without a separate visit-ID cursor. Unknown delivery outcomes count as failures; quota deferrals stay distinct. Manual runner callers retain default behavior when the optional scheduler callbacks are omitted. |
| A08/A09 Replies | The GET route claims before sync/draft provider work. Its global business/location keyset rotates through tenants; a per-business unit cursor stores the active location, stage, review key, connection version, and sweep counters, and is resumed after the keyset wraps. Checkpoints follow persisted sync/draft units; failed locations report `partial` or `failed`. Manual review workflows retain default provider timeouts/signals. The notification cursor avoids blind replay, but no durable alert-email outbox exists. |

## Remaining decisions and scope

Migration 027 registration/application, old-worker drain, monitor invocation schedule, Neon/client statement timeout, and whether privacy retention should be scheduled with an explicit cadence are integration decisions. A11 account deletion stays disabled until its cross-route guards and in-flight job drain are integrated. Replies notification email has no durable outbox: an indeterminate accepted result is recorded as a failure and not blindly resent; a crash between review persistence and saving the notification stage can also lose a notification. A10/A17 must decide whether to add an outbox. The A12 roadmap also includes global error-boundary and operator support-inbox work; those features are outside this cron-health patch and remain unimplemented here. No dependency or shared model change is required beyond the proposed database objects and additive health response fields.
