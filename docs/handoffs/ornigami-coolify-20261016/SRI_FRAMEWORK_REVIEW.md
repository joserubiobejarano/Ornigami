## Why configuration or a standalone source edit is insufficient

Next's `experimental.sri.algorithm` already has the reviewed SHA-256 setting. Its installed webpack plugin generates an integrity manifest. Bootstrap/preinit script paths consume that manifest, but layer and boundary script emitters omit the integrity property. The [16.4.1 layer emitter](https://raw.githubusercontent.com/vercel/next.js/v16.4.1/packages/next/src/server/app-render/get-layer-assets.tsx) demonstrates the gap. The newer supported [16.4.2 layer emitter](https://raw.githubusercontent.com/vercel/next.js/v16.4.2/packages/next/src/server/app-render/get-layer-assets.tsx) and [component emitter](https://raw.githubusercontent.com/vercel/next.js/v16.4.2/packages/next/src/server/app-render/create-component-styles-and-scripts.tsx) still omit it. That release is tag commit `2864b1772c37242a9b40ab4d366eb7d368c2a070`; an upgrade alone is not a demonstrated SRI fix.

In Node production, `dist/server/route-modules/app-page/module.compiled.js` selects a precompiled `app-page.runtime.prod.js` bundle (or its configuration-specific counterpart). The installed bundle's source map includes the same component emitter. Editing only `dist/server/app-render/*.js` would therefore miss the production renderer. The identity receipt records the actual installed bundle and source-map hashes. No ignored `node_modules` patch was used to produce a passing result.

There is also a broader loading path to cover in any full fix: the freshly generated webpack runtime creates script elements and assigns their source without an integrity property. The captured runtime contains no integrity literal. This is source/output inspection, not a browser navigation acceptance test. The Pages Router's separate `route-loader` is similarly incomplete, but it is not evidence that this App Router uses that loader. A server-tag-only repair must not be represented as complete browser chunk protection.

## Concrete alternative for review

Recommend an application-owned, checksum-pinned framework package built from the reviewed official Next 16.4.2 source tag, with a narrow, maintained SRI patch and its source/build provenance committed for review. This preserves the existing Next architecture, Node supervisor, CSP and image contract. It adds framework maintenance responsibility, so it is proposed rather than silently adopted.

The proposed implementation and acceptance boundary are:

1. Update `get-layer-assets.tsx` and `create-component-styles-and-scripts.tsx` to obtain each script's SHA-256 integrity from `ctx.renderOpts.subresourceIntegrityManifest`, retaining the existing nonce, source and crossorigin behavior. In an admitted production SRI build, missing or malformed entries must fail rather than silently emit an unprotected script. Keep development behavior explicit.
2. Rebuild the actual Node production renderer bundles through the framework's build pipeline. Package the result as an app-owned versioned tarball with its digest/integrity pinned in the lockfile; record upstream commit, patch, licenses and generated-bundle hashes. Do not patch opaque minified strings during app startup, fetch mutable code, or rely on changes in an ignored local installation.
3. Complete the webpack/browser chunk loader's integrity mapping before appending dynamically loaded scripts, using hashes from the final emitted bytes. Preserve nonce propagation and reject absent entries. Verify interaction with React preinit, app navigation, error/not-found boundaries and Sentry's final asset transforms; do not assume build-time manifest existence is enough.
4. Prove fresh-build HTTP coverage for every emitted script on home/login plus boundary routes, then browser navigation/lazy-loading coverage. Tamper with one served script through a local test interceptor and verify the browser rejects it; verify missing-manifest entries fail closed. Keep nonce rotation, CSP without unsafe script allowances, and all existing negative security checks. Preserve source maps and static CSP parity.
5. Only after that review and local evidence, propose one bounded external Linux amd64 image trial with the accepted 8 GiB/3 CPU/4096 MiB heap, retained maps, scans, existing diagnostic retention and independent restart/cache checks. No limit increase or retry is implied. The framework package becomes another dependency requiring advisory monitoring and an upstream-removal plan.

This is a concrete contract-preserving alternative to the stock framework limitation. Nonce-only acceptance, removing SRI assertions, permitting unsafe scripts, and response rewriting at Traefik are not proposed. Waiting for an upstream release that passes the same tests is also viable; merely selecting a newer version is insufficient evidence.

No Linux diagnostic experiment is necessary to establish the current emission gap: the fresh Node 22 build and framework source agree. A later Linux trial would test a reviewed changed framework package plus the native/container contract, not rediscover the same missing attributes. Before requesting it, identify that exact package/source and the hypothesis: all protected script paths now emit/use verified hashes while CSP, sharp, resource bounds and cache persistence remain intact. Expected evidence would be complete script coverage, corruption rejection, raw base/final scan reports and the existing runtime/resource receipts. No such run is requested or queued here.
