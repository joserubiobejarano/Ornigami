## Complete inventory, scanning and resource evidence

The proposed workflow requires **nine roles**: original tooling parent, original runtime parent, build-base (including upgraded npm), deps, builder, prod-deps, runner, BuildKit and Dockerfile frontend. Each gets config/layer identity, complete filesystem hashes, package manifests, static native closure, full Trivy package inventory and all-severity vulnerability results. Intermediate npm package inventory is mandatory; zero final language findings cannot establish builder safety. No shared-host scans or builds are used.

OS package inventory remains mandatory for OS images. For a bare Go Dockerfile frontend, absent OS metadata is accepted only when its hash-bound complete filesystem proves **every** native object has a corresponding Go package inventory target. Missing, unknown, extra or mismatched native coverage fails. This is coverage for an OS-less executable, not a vulnerability suppression. Critical/high counts must still be zero in every role; all reports remain retained. The old frontend pin could itself contain advisories and must fail the same threshold if found.

Inventory and vulnerability scans run **serially**, each in its own **2 GiB / 1 CPU / zero-swap** scope with start/end timestamps, limits, peak/current memory, memory events/stat/pressure, CPU, PID counters and exit status. The compiler never overlaps these phases. DB age/hash and pinned Trivy identity are enforced. Parent scans precede compilation; diagnostic functional tests may continue after a fully collected advisory failure, while the independent aggregate security gate remains failed. After a successful primary build, intermediate exports use its existing cache, exact arguments and the same bounded BuildKit; a failed initial build prohibits exports/recompilation. Final scanning reuses the single existing final archive/report.

Cache exports reject malformed progress, noncached RUN events and missing affirmative cached-target evidence. They have their own time/resource observations. **BuildKit can start work before publishing a progress event**: the abort guard does not prove no process started. Exact progress protocol/cache retention/export behavior remain Linux feasibility risks. Any failure means incomplete evidence and no acceptance; no cold rebuild or automatic retry is allowed. A safer multi-target single-solve alternative would need separate preparation/review if this proves unreliable.

BuildKit remains **8 GiB / 3 CPU / zero swap**, serial worker, Node heap **4 GiB**, source maps retained. Runtime remains **768 MiB / 0.75 CPU**, heap approximately 512 MiB. The workflow adds timestamped two-second observations of the exact owned BuildKit cgroup and its process RSS/PSS without command arguments/environment; whole-build counters survive failure. The prior exact 8 GiB peak and three limit events remain unattributed. New observations may distinguish compiler/native/cache activity; **no headroom is claimed**. One full compile only, a 24-minute work deadline, 40-minute job timeout, 20 GiB free-disk reserve and bounded scan phases stop rather than increase limits. Raw image layers/spools stay outside uploaded evidence and are removed only with checked ownership; stopped workers' leftovers are separately accounted for during cleanup.

Capture still requires qualified cold/restart/recreation receipts and a nonempty persistent summary. Scan indexes now also require source identity, exactly nine roles and the receipts behind claimed-complete stages. Truncated JSON, wrong JSON types, mismatched source or missing receipts preserve the invalid index and fail **after** a hashed manifest is written. Unreached phases are explicitly skipped/unverified. Custody is always `not-assessed-by-capture`; an owner acknowledgment would be a separate future authorization and cannot establish completeness/security.
